# ADR-0015: KV-T —— 全局时间戳、serializable 跨 Region 事务与严格透明 Watch

- 状态：accepted
- 日期：2026-10-18
- 决策者：维护团队 / 架构评审
- 评审记录：issue #128（接受 ADR、裁定 v2 集群服务边界）、issue #129（D12 协议口径）。
  这两项的结论并入本文，不另建第二份口径。

## 背景

### 目标

coord 当前的多 Region KV 是「每个 Region 独立 revision、跨 Region Txn/Range/Watch 显式拒绝、Region 表静态、无在线 Split/Merge」的形态。业务侧要把它当成通用 KV 使用，必须补上：

1. 通用 KV Region 的**任意 key** 在线 split/merge；
2. **serializable** 跨 Region 事务（不是只读快照或 SI）；
3. **严格透明** 的跨 Region Watch：全局序、同一事务多 key 原子可见、split/merge 不丢事件、不要求应用 re-list；
4. 受影响数据面 API **全量 v2**；
5. **不做 v1 数据迁移**：只支持 greenfield v2 集群；
6. MQ v2 在 KV-T 落地后提供，不提前 GA。

本 ADR 固定上述目标与不可逆的语义口径。实施计划、任务拆分与工期由后续 PR 维护；本 ADR 不把实施细节写成第二份计划。

### 约束

- **ADR-0001**：未经生产验收的能力面默认关闭；KV-T 在 GA 前必须显式启用，不得静默替换 v1。
- **契约纪律**：`apis/contracts/WHITEPAPER.md` §4/§10/§11；新增/变更 wire 必须走契约流程，禁止解析错误文案。
- **ADR-0004**：Raft 日志回收以快照为锚；KV-T 的 Commit Log 不是 Raft log，必须有独立的保留/GC。
- **ADR-0010**：既有边界保持语义稳定；本 ADR 是新增能力，不静默扩大既有承诺。
- **不做迁移**：只支持 greenfield v2；v1 包冻结，不作为 v2 集群的数据面。
- **多 Region 现状**：v1 的 Region 表静态、无在线 Split/Merge；KV-T 必须把动态 Region 表/epoch 作为前置能力。
- **实现成本**：serializable + 严格 watch + 任意 split/merge 是分布式事务 KV 量级，不是 MQ 的附加项。

### 备选方案与取舍

| 方案 | 内容 | 不采用的原因 |
|:--|:--|:--|
| **S：存储层任意 split/merge** | 任意 key 搬迁，但 Region 仍是一致性单元；跨 Region Txn/Range/Watch 继续拒绝 | 不满足「应用透明」；split 后原本同区的操作会变成跨区错误 |
| **Per-Region revision base** | 每个 Region 用 `base + log_index` 作为 revision，split 新 Region 领新 base | 不能解决 merge 的 changelog revision 冲突，也不能给跨 Region 快照/事务提供全序 |
| **Percolator SI** | 2PC + 快照隔离 | 只提供 SI，允许 write skew；不满足 serializable |
| **单组 Global Commit Log** | 所有 commit 写一个 Raft log | 写吞吐单点；D5 选择直接分片 |
| **W1：per-Region watch + commit_ts 标记** | 不做全局总序/原子多 key | 不满足「严格透明」；split/merge 仍要求 re-list |
| **v1 → v2 迁移** | 双写/映射 revision/在线迁移 | 成本高且不可靠；D7 选择 greenfield v2 |
| **MQ v2 提前 GA** | 在共享基础先交付 MQ | 会让 MQ 在 KV 语义仍变化时对外承诺；D8 选择 KV-T 后提供 |

## 决定

### D1 目标形态：应用透明的分布式事务 KV（T）

- coord KV 的目标形态是 **T**：任意 key 在线 split/merge、serializable 事务、严格透明 watch、v2-only、无迁移。
- 本 ADR 不接受把 S 包装成 T；如果实现 gate 无法满足 T，必须**新增 ADR 明确降级**（S/SI/W1），不得静默改变语义。
- 非目标：SQL/查询优化器、跨地域多活、全球一致性、exactly-once、Kafka wire protocol 兼容、通用流处理/连接器生态。

### D2 全局 TSO

- 引入全局 **TSO（Timestamp Oracle）**，为 `start_ts` / `commit_ts` / `read_ts` 提供全局单调时间戳。
- 首个交付阶段的 TSO 状态机挂在 **region 0 system raft**；独立 TSO Raft group 是后续扩容项，不是第一版承诺。
- TSO 按批分配 `[start,end)`；节点本地递增发放。批次只保证全局唯一/单调，允许空洞，**绝不允许复用**。
- TSO 批次在重启/换 leader 后未用完的部分直接丢弃；新批次必须大于所有已发放值。
- `commit_ts` 是写事务的 revision；同一事务的所有 key 共享同一个 `commit_ts`。
- TSO 的高可用、批量大小、持久化与故障切换属于实现细节；语义口径由本决定固定。

### D3 Revision 模型：全局 `commit_ts`，与 raft log index 解耦

- `revision = commit_ts`；`create_revision` / `mod_revision` 使用 `commit_ts`。
- `Watch.start_revision` = `commit_ts`；`Range` header revision = `read_ts`；`Compaction` 水位 = `safe_ts`。
- `MvccStorage` 必须持久化 `META_CURRENT_REVISION`（或等价状态），`current_revision()` 不再等于 per-Region raft log index。
- `apply_compact` 不得再用 `applied.index` 钳制 revision；必须按 TSO current revision 钳制。
- Snapshot 必须携带 TSO/current revision 状态；恢复后 TSO 继续单调，revision 不倒退。
- v2 从第一天就是 TSO 语义；v1 revision 不兼容、不迁移。

### D4 Serializable：OCC 读集/谓词校验 + 全局 Commit Sequencer

- 承诺 **serializable**，不承诺 strict serializability（外部实时序）。
- 采用 **OCC**：事务读阶段记录 point read set 与 range read set；commit 前校验 `(start_ts, commit_ts]` 内是否有写命中读集/谓词；冲突 abort/retry。
- **全局 Commit Sequencer** 是 serializable 的串行化点：
  - 单 Raft 组，按进入顺序校验并分配 `commit_ts`；
  - 校验通过后写 `CommitDecision`；
  - 校验失败返回冲突，不写决策；
  - 用户级冲突不得让 apply 返回 `Err`（不得 wedge raft）。
- **Commit Log 可以分片存储/watch 读取，但 OCC 校验不能分片**：
  - 如果两个冲突事务落在不同 shard、各自校验，会同时通过，serializable 不成立；
  - 要让校验也分片，必须换协议（按冲突域分区 / strict 2PL / 分布式 SSI），不在本 ADR 承诺内。
- Range 读需要**谓词校验**（防幻读）；`ValidationIndex` 必须支持 `range [start,end)` 在 `(start_ts, commit_ts]` 是否有写。大范围读/大读集必须有上限，超限拒绝或要求拆分事务。
- 事务有 TTL；长事务不得无限阻塞 split/merge 或锁清理。

### D5 严格透明 Watch：分片 Commit Log + 完整 change record

- Watch 必须满足：
  1. 事件按 `commit_ts` 全局有序；
  2. 同一事务的多个 key 变更原子可见（同一批次）；
  3. split/merge 不丢事件、不要求应用 re-list；
  4. `start_revision` 跨 split/merge 连续；
  5. 历史窗口不足返回 `HISTORY_UNAVAILABLE`，不静默丢。
- 实现口径：
  - **Commit Log 按 `commit_ts` 区间分片**，每个 shard 一个 Raft group；
  - **CommitRecord 存完整 change record（key + value）**，Watch 不依赖 Region 历史；
  - **Watch Coordinator** 按 shard 顺序读，按 `commit_ts` 输出；同一事务的 changes 作为一个原子批次；
  - **seal/watermark**：`CommitWatermark = min(in-flight commit_ts) - 1`；`watermark >= shard.end_ts` 时 shard sealed；Watch 只推进到 sealed shard 末尾；
  - 默认保留窗口 24h（可配 1h–7d）；超出窗口 → `HISTORY_UNAVAILABLE`。
- 分片的是 **存储与 watch 读取**；全局顺序仍由 Commit Sequencer 决定。不得把“分片”解释为“校验也分片”。

### D6 任意 key 在线 Split/Merge

- 支持通用 KV Region 的任意 key split/merge；split_key 不要求落在 MQ partition 边界。
- 前置能力：
  - 动态 Region 表（region 0 权威元数据，所有 server 收敛）；
  - 运行时 `spawn/remove/update range`；
  - `routing_epoch` / `EPOCH_STALE`；
  - PD Split/Merge operator 从 unsupported 改为真实执行；
  - intent/recovery：server 重启后能从前一轮 intent 继续或回滚。
- Split/Merge 必须：
  - split 前 drain 该范围的活跃事务锁/intent（等待 commit/abort 或 TTL 过期）；
  - 搬迁 MVCC 行、lease 元数据、必要的对象 manifest/chunk；
  - cutover 后旧 epoch 请求返回 `EPOCH_STALE`，不允许双写/双读；
  - 已 commit 的 key 不丢、不双写、revision 不倒退。
- **`/obj/` 例外**：对象存储使用独立 Region 区间，不参与任意 KV split；SplitChecker 必须跳过。对象存储的扩展/容量管理单独做。落地：`[kv_t].enabled` 与 `[object_storage].enabled` 同时启用时，在表种子期把 `[/obj/, /obj0)` 从 `multi_raft.initial_regions` 切成独立固定 Region（`storage::region_table::carve_object_region`）；SplitChecker/MergeChecker 不产生命中它的 operator，`plan_split`/`plan_merge` 仍拒绝（#165）。
- 落地（G5）：权威表是 region 0 MVCC 的单键 `/_sys/pd/regions`，经
  `Command::RegionMeta(RegionMetaOp)` 提交；split/merge 的 add/update/remove 必须在
  同一个 raft 条目里成批生效（区间平铺 / epoch 单调校验，非法批整批拒绝且不让
  apply 返回 `Err`）。各节点在 KV 入口按表版本刷新 `RegionManager`；运行时 spawn
  与 PD 对账分别由 #160/#162 交付。
- 落地（D7 的 `coord.storage.v2`，G5）：manifest 行以全局 `commit_ts` 写进固定
  `/obj/` Region（`Command::ObjectStoreV2`，chunk 文件与 manifest 行在同一条 raft
  条目里落盘）；`read_ts` 快照读 manifest，chunk 字节不随 revision 版本化（历史
  chunk 被覆盖/删除时返回 `OUT_OF_RANGE`）。v2 集群不注册 v1 `coord.storage`
  （v1 写路径以 raft log index 当 revision，会与 `commit_ts` 撞 changelog 键）。
- 落地（G5 cutover 连续性）：split 目标导入完成时把 `DECISION_APPLIED_TS` 钉到
  导入水位，后续决策在目标 Region 续跑；split 源与 merge 两侧在搬迁前要求
  `last_applied_decision_ts == current_revision`，merge 还要求两侧
  `current_revision` 相等，否则 fail-closed 重试。Watch 对同一 `commit_ts` 的
  跨 Region 重放记录按 key 去重（cutover 窗口内同一决策可能先在父 Region apply、
  再在子 Region 重放），cursor 不因拓扑变化跳变。**仍 open**：跨协调节点会话
  drain 与迁移窗口内的直接 KV 写冻结。

### D7 API：受影响组件全量 v2，v1 冻结

- 受影响的数据面组件使用 v2：
  - `coord.kv.v2`
  - `coord.txn.v2`
  - `coord.watch.v2`
  - `coord.mq.v2`
  - `coord.lease.v2`
  - `coord.storage.v2`
- `coord.tso.v2` 是 v2 数据面的**时间戳原语**（不是业务组件）：对外只暴露批次
  分配与单值获取，权限独立（`data:tso:allocate`）；普通调用方不需要直接使用它
  （事务由服务端分配 start_ts，范围读默认取 safe_ts）。
- 不受 TSO/revision/跨 Region 语义影响的服务保持原版本：registry / config / lock / election / idgen / policy / pki / transit / circuitbreaker / ratelimiter / featureflags / event / scheduler。
- workflow 如果内部改用 v2 KV 但公共语义不变，可继续使用 `coord.workflow.v1`；若它暴露 revision/TSO 语义，再升级 v2。
- v1 冻结：不在 v2 集群服务；不实现 v1→v2 双写/映射/迁移工具。
- 只支持 greenfield v2；备份/恢复/快照只保证 v2。

### D8 MQ v2 顺序：KV-T GA 后提供

- MQ v2 不在 KV-T 完成前对外 GA；不采用“共享基础提前交付”的路线。
- 内部可在 Split/Merge 与严格 Watch 基础可用后做设计/原型，但 release gate 绑定 KV-T GA。
- 预期总交付：KV-T 约 40–52 个月（5–6 人）；MQ v2 在 KV-T GA 后 +10–12 个月；合计约 50–64 个月。
- MQ v2 的 `coord.mq.v2` 契约、group coordinator、workflow trigger/dispatcher 由后续 ADR/契约页维护；本 ADR 只固定顺序依赖。

### D9 固定口径（默认参数）

以下为冻结的默认值；允许用基准微调数值，但不得改变语义。语义变更必须新增 ADR。

| 项 | 默认口径 |
|:--|:--|
| Commit Sequencer | 单 Raft 组；批量校验/提交，默认 256 commits/批 |
| Commit Log shard | 1,000,000 条 CommitRecord 或 1 小时，先到先 seal；80% 预创建下一个；seal 超时 5 分钟 |
| Shard seal | `CommitWatermark >= shard.end_ts`；watermark = `min(in-flight commit_ts) - 1`（无 in-flight 时 = max_committed_ts） |
| CommitRecord | 完整 key+value；zstd 压缩；单事务上限 4MB |
| Watch 保留 | 默认 24h，可配 1h–7d；超出 `HISTORY_UNAVAILABLE` |
| ValidationIndex | 每 shard：key → max_commit_ts 哈希索引 + range 区间索引；快照 + Commit Log 重建 |
| Watch cursor | `(shard_id, commit_ts)`；单批 ≤1000 条或 1MB；原子多 key 不拆批 |
| `/obj/` | 独立 Region 区间（表种子期从 `initial_regions` 切出，id = 种子最大 id + 1）；SplitChecker/MergeChecker 跳过；不参与任意 KV split |
| 迁移 | 不做；greenfield v2；v1 冻结 |

### D10 交付 gate 与降级

- 必须按 gate 推进；每个 gate 都有“停止/回退”的选项，不得用沉没成本掩盖不达标：
  - G0 契约冻结；
  - G1 TSO/revision；
  - G2 跨区 Range/SafeTs；
  - G3 serializable OCC + Commit Sequencer；
  - G4 严格 Watch + 分片 Commit Log；
  - G5 Split/Merge；
  - G6 KV-T GA；
  - G7 MQ v2 GA。
- 如果 G3/G4 无法满足 T，必须新增 ADR 明确降级到 SI/W1 或 S；不得静默改变 `serializable` / `严格透明` 的承诺。
- 如果 G1/G2 无法满足，KV-T 不进入 GA；MQ v2 不启动对外阶段。
- **G2 跨 Region Range 的跨节点语义**：v2 Range 是快照读，不要求请求节点是任何
  Region 的 leader。请求先把 `read_ts` 解析/等待到 `<= 本节点 safe_ts`（D12.1/D12.3），
  再在本地各 Region 副本的精确快照上读；每个分段复核 `read_ts <= 本地 applied`，
  不足时 `UNAVAILABLE + SAFE_TS_LAG`（可重试），整请求失败、不返回部分结果。
  前提是请求节点持有命中 Region 的本地副本（v1 静态复制下每个节点持有全部 Region）；
  副本缺失/路由缺口同样整请求失败。split/merge 的 routing epoch 校验归 #161/#167。
  `read_ts=0` 取**本节点** `safe_ts`，不是线性一致读；跨节点同一快照或
  read-your-writes 必须使用显式 `read_ts`。

### D11 不变量

以下不变量在任何实现/重构中必须成立：

1. `commit_ts` 全局唯一、单调；同一事务所有 key 共享同一 `commit_ts`。
2. 同一 key 的 `mod_revision` 单调递增；split/merge/重启/快照恢复后不倒退。
3. TSO 批次不复用；空洞允许。
4. v2 写命令的 `commit_ts <= current_revision` 且未命中已有 revision 时必须显式拒绝（`CommitRejected`），不得静默写。
5. 用户级冲突/拒绝不得让 Raft apply 返回 `Err`。
6. 同一 `commit_ts` 的命令重放不得重复写 changelog / 重复推进 revision。
7. Watch 全局序按 `commit_ts`；同一事务的 changes 原子批次；窗口不足返回 `HISTORY_UNAVAILABLE`。
8. Split/Merge 不允许同一 key 同时由旧/新 Region 双写或双读；旧 epoch 必须 `EPOCH_STALE`。
9. `/obj/` 不被任意 KV split 命中；对象 chunk 不随 KV split 迁移。
10. v1 数据不迁移；v2 集群不接受 v1 revision 语义。

### D12 协议口径（#129 裁定）

本决定把 D2–D5 落到可实现的 wire 口径。字段级语义以
`apis/contracts/proto/coord/<domain>/v2/*.proto` 头注为单一归属；此处只裁"谁做、
失败返回什么"。

#### D12.1 start_ts / read_ts / commit_ts 的获取

- **TSO 服务**：`coord.tso.v2.TSO`（`Allocate` / `GetTs`）。`Allocate` 只由 region 0
  leader 处理（非 leader 返回 `NOT_LEADER`），批次 `[start_ts, end_ts)` 由持久化
  高水位发放；`GetTs` 可由任意节点从本地批次缓存直接发放（#137）。
- **事务**：`coord.txn.v2.Txn.Begin(start_ts=0)` 由服务端向 TSO 申请；显式
  `start_ts > 0` 允许（高级客户端从 TSO 批次取得），服务端不再二次分配。
- **快照读**：`Range(read_ts=0)` 取**请求节点**当前的 `safe_ts`（本地副本的最小
  applied 水位）；显式 `read_ts` 用于跨 Region 一致性读，必须来自 TSO。`read_ts=0`
  的快照可能落后于集群最新提交，且跨节点不保证同一数值/单调；需要跨节点同一快照
  或 read-your-writes 的调用方必须使用显式 `read_ts`（D12.3）。
- **写时间戳**：`commit_ts` 由 **Commit Sequencer** 在决策时分配（D4）；
  `coord.kv.v2` 的直写接口要求调用方自带 `commit_ts`（内部/高级路径），
  普通业务写入走 `coord.txn.v2`。
- **client 缓存责任**：批次是进程内内存态，重启即丢弃；**服务端保证绝不复用**，
  因此客户端无须为"不重用"做持久化。若某个 SDK 选择持久化批次，必须在发出
  任一值之前把高水位落盘，且崩溃后不得复用残留值；SDK 默认不持久化。

#### D12.2 OCC 读集：服务端会话

- 读集由**服务端**在 `Begin` 创建的会话里保存：`Read` 在 `start_ts` 快照上读并把
  point key / range 谓词记入读集；`Commit` 把读集 + 写集交给 Commit Sequencer。
  客户端不携带读集 ⇒ 无法通过省略读集条目规避冲突。
- 会话归属**协调节点**（不复制）：协调节点崩溃/重启或 TTL 到期 ⇒ `ABORTED` +
  `TXN_NOT_FOUND`，客户端重跑整个事务。事务原子性不受影响：commit 是 Sequencer
  的单次决策，会话丢失只会导致重跑，不会产生部分提交。
- 上限：写集 ≤ `max_txn_bytes`（4MiB，超限 `TXN_TOO_LARGE`）；读集条目 ≤
  `max_read_set`（4096）；单次 range 读 ≤ `max_range` 个 key（默认 10000）；
  超限 `INVALID_ARGUMENT` + `READ_SET_TOO_LARGE`。`Commit.request_id` 在 TTL 内幂等。
- 冲突返回 `ABORTED` + `TXN_CONFLICT`，**不写** `CommitDecision`；用户级冲突不得让
  Raft apply 返回 `Err`（D11.5）。

#### D12.3 CommitDecision 可见性

- `Commit` 在 CommitDecision **持久化后**返回 `commit_ts`，不等各 Region apply。
- 全局 `safe_ts` = 各 Region 已 apply 的 `commit_ts` 水位的**最小值**（region 0 汇总/
  发布）；`read_ts <= safe_ts` 的读保证看到所有 `commit_ts <= read_ts` 的事务
  （同 Region 按 `commit_ts` 顺序 apply，跨 Region 由 safe_ts 收敛），因此不会
  出现"同一事务部分可见"。
- `read_ts > safe_ts` 时服务端等待至多 `read_ts_wait_ms`（默认 2000ms）；超时返回
  `UNAVAILABLE` + `SAFE_TS_LAG`（可重试）。
- read-your-writes：客户端用 `read_ts >= commit_ts` 读，并在 `SAFE_TS_LAG` 时重试；
  服务端不阻塞 Commit 等待 apply。

#### D12.4 TSO 批次语义

- 批大小默认 1024（`[kv_t].tso_batch_size`），上限 65536；只增不减、允许空洞、
  **绝不复用**；重启/换 leader 丢弃未用完部分，新批 `start_ts` 必须大于已发放
  上界（高水位随 region 0 状态机持久化）。
- 单节点缓存 `[next, end)`，剩余低于阈值时预取；leader 切换/超时重试不改变已发放
  区间；`GetTs` 耗尽且申请失败返回 `UNAVAILABLE`（可重试）。

#### D12.5 错误与路由

- v2 新增结构化码与状态映射见 `apis/contracts/WHITEPAPER.md` §6.1.1：
  `TXN_CONFLICT` / `TXN_NOT_FOUND` / `TXN_TOO_LARGE` / `READ_SET_TOO_LARGE` /
  `COMMIT_REJECTED` / `EPOCH_STALE` / `HISTORY_UNAVAILABLE` / `SAFE_TS_LAG`。
  调用方只按码分支，禁止解析消息文本。
- Region 路由 epoch 通过请求 metadata `coord-routing-epoch` 传递；与节点缓存不一致
  返回 `ABORTED` + `EPOCH_STALE`，客户端刷新路由后重试（D6 的 cutover 守卫生效）。
  - 取值是**权威 Region 表的 `version`**（全局路由版本），不是 per-Region 的
    `RegionEpoch{conf_ver, version}`：一个 u64 表达不了一对分量，而 Range/Txn 的
    一次请求在 split 后可能横跨 version 不同的两个 Region。
  - 全部 v2 数据面服务（KV/Txn/Watch/Lease）在 handler 入口校验；metadata 缺失
    不校验（单 Region / 尚未学到版本的客户端）。不一致（客户端过旧，或本节点尚未
    apply 到该版本）→ `ABORTED` + `EPOCH_STALE`，trailing metadata 回传本节点当前
    `version`；非法值 → `INVALID_ARGUMENT`（不静默忽略）。

### D13 v2 集群服务边界（#128 裁定）

- **v1 数据面不服务**：v2 集群不提供 `coord.kv` / `coord.txn` / `coord.watch` /
  `coord.lease` / `coord.storage` 的 v1 语义（D7 字面执行），**不做兼容 facade**。
  v1 包冻结：不修 bug 之外不新增能力，保留给既有 v1 集群。
- **能力矩阵（KV-T GA 时）**：

  | 能力 | v2 集群状态 |
  |:--|:--|
  | KV / Txn / Watch / Lease / Storage v2 | 可用（`[kv_t].enabled=true` 且对应 gate 已交付） |
  | TSO（`coord.tso.v2`） | 可用（内部原语；普通调用方不需要） |
  | MQ v1 | 不可用（fail-closed，不注册/一律拒绝） |
  | MQ v2 | 未 GA（G7；KV-T GA 后另立 ADR） |
  | workflow durable（依赖 MQ 的路径，如 MQ trigger） | fail-closed；纯 KV/审批路径在 Agent 迁移到 v2 后可用 |
  | registry / config / lock / election / idgen / policy / pki / transit / circuitbreaker / ratelimiter / featureflags / event / scheduler | 语义不受 TSO/revision 影响，随 Agent 迁移到 v2 数据面后可用（#170/#171） |

- **无迁移**：greenfield v2；v1 数据不迁移；备份/恢复只保证 v2；升级路径 = 重建
  v2 集群。回滚边界：v2 集群不能回退到 v1 数据面；需要回滚时保留旧 v1 集群，
  而不是在 v2 上降级。
- `[multi_raft].legacy_migration` 是 **v1 单 Raft → multi-raft** 的迁移，不是
  v1→v2 迁移；v2 模式下必须拒绝（`[kv_t].enabled=true` 与
  `legacy_migration=true` 互斥，启动失败），`allow_unmigrated` 同理不适用。

## 后果

### 收益

- coord 从“multi-raft KV”升级为支持任意 key 在线分裂/合并、serializable 跨 Region 事务、严格透明 watch 的分布式事务 KV。
- MQ v2、workflow trigger、对象存储等上层能力可以建立在统一 TSO/revision/Region 机制上，不再各自打补丁。
- v2-only + 无迁移移除 v1 revision 兼容分支，长期代码更简单。
- 分片 Commit Log 为 Watch/审计保留提供独立扩展面；完整 change record 使 split/merge 不依赖 Region 历史。

### 代价与风险

- **工作量**：KV-T 约 40–52 个月（5–6 人）；MQ v2 再加 10–12 个月；这是多年平台项目，不是单个季度 feature。
- **Commit Sequencer 是串行化点**：serializable 要求全局校验；单 Raft 组可能成为吞吐瓶颈。后续按冲突域分区需要新协议/新 ADR。
- **OCC 谓词校验成本**：大范围读/高冲突场景重试多；必须限制读集/Range 大小并做基准。
- **Commit Log 写放大**：完整 value 在 MVCC 与 Commit Log 各存一份；保留窗口默认 24h，仍需容量评估。
- **Shard seal/watermark**：seal 停滞会阻塞 Watch；需要 in-flight commit 跟踪、超时 abort、监控。
- **Split/Merge 与锁**：drain 活跃事务会阻塞 split；需要事务 TTL 和上限。
- **无迁移**：v1 用户不能升级，只能重建；这是产品/运营决策，必须在发布说明中明确。
- **v2 API 双份维护**：受影响组件全量 v2；v1 冻结但不维护新功能。
- **`/obj/` 例外**：任意 KV split 对对象存储不成立；对象存储需要独立扩展/容量管理。

### 与既有 ADR 的关系

- 不推翻 ADR-0001/0002/0004/0010/0013/0014；KV-T 在这些边界之上新增能力。
- ADR-0001 的“默认关闭”仍适用：KV-T 在 GA 前必须显式启用，不得静默替换 v1。
- ADR-0004 的 Raft 日志回收不变；Commit Log 是独立日志，按本 ADR 的保留窗口 GC。
- ADR-0010 的既有消费方边界保持稳定；KV-T 是新增平台能力，不静默扩大既有承诺。

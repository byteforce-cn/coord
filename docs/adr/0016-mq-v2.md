# ADR-0016: MQ v2 —— 分区日志、消费组与工作流触发

- 状态：accepted
- 日期：2026-10-29
- 决策者：开发负责人（维护者 2026-10-29 授权直接签字）；G7 启动 gate #178
- 评审记录：#178。设计与任务拆分见
  `docs/superpowers/specs/2026-10-29-mq-v2-design.md`；本文只固定不可逆的决定。

## 背景

### 目标

MQ v2 是 v2 集群上的**持久化分区日志**：分区内有序、至少一次消费、服务端消费组
协调、按时间/容量保留、显式死信，并作为 v2 工作流的触发源。它只服务 v2 集群，
不要求 Kafka wire 兼容，也不做 v1 数据迁移。

### 现状事实

| 事实 | 现状 | 证据 |
|:--|:--|:--|
| MQ v1 是 Agent 本地存储 | 每个 Agent 一个 redb；`Publish` 只承诺落本地日志 | `coord-agent/src/services/mq.rs` |
| 分区 Leader 是静态指派 | ISR 成员中地址最小者；无自动故障转移 | `coord-agent/src/services/mq.rs` |
| 消费位点是 Leader 本地状态 | `Ack` 只写分区 Leader；无迁移/复制 | `coord-agent/src/services/mq.rs` |
| 没有真正的消费组 | `consumer_group` 只是位点命名空间；无成员/再平衡/代际 | `apis/contracts/proto/coord/mq/v1/mq.proto` |
| `Subscribe` 是 best-effort | 背压时丢弃；`Poll` + `Ack` 是唯一至少一次路径 | 同上 |
| 容量上界是逐写严格 | 消息 + DLQ 同事务记账；超界拒绝 `RESOURCE_EXHAUSTED` | `docs/production/ops/boundaries.md` B-PL-4 |
| KV-T 已提供 v2 基座 | Region 表、Raft 组、快照/备份、TSO/Txn/Watch、Agent v2 代理 | `docs/adr/0015-kv-t.md` |
| G7 顺序依赖 | MQ v2 的 GA 不早于 KV-T GA；设计/原型可提前 | `docs/adr/0015-kv-t.md` D8/D10 |

### 约束

- **ADR-0001**：默认关闭；`[mq_v2].enabled=false` 时 v1 行为、磁盘布局、服务注册
  字节级不变。
- **ADR-0015**：v1 数据面冻结；v2 集群不服务 MQ v1；MQ v2 只支持 greenfield v2；
  G7 的 release gate 绑定 KV-T GA。
- **ADR-0004**：Raft 日志回收以快照为锚；MQ 的段日志是状态机状态，不是 Raft log。
- **契约纪律**：`apis/contracts/WHITEPAPER.md` §4/§10/§11；字段语义的单一归属是
  `coord.mq.v2` proto 头注；错误码只按码分支，不解析文案。
- **不迁移**：MQ v1 → v2 不迁移；v1 集群继续用 v1，v2 集群从空 topic 开始。

### 非目标

Kafka wire 兼容、exactly-once、全局（跨分区）顺序、连接器/流处理、多集群复制、
MQ v1 数据迁移、每分区在线 split/merge、自动分区再平衡、消息体压缩、跨分区事务。
这些都需要另立 ADR 或版本公告。

### 备选方案与取舍

| 方案 | 内容 | 不采用的原因 |
|:--|:--|:--|
| **KV 承载日志** | 消息写 v2 KV，offset 取 `commit_ts` 或计数器 | MVCC 写放大、保留期只能靠逐 key tombstone/DeleteRange，`DeleteRange` apply 成本随存活 key 线性增长；配额/幂等无法在 apply 内严格原子。适合小 topic，不作为 v2 主路径 |
| **一分区一 Region** | 每个分区独立 Raft 组，天然隔离 | 分区数直接放大 Region/副本数；`CreateTopic` 进热路径创建 Region，v2.0 风险过高。留作隔离增强 |
| **静态 ISR（v1 原样）** | 最小地址当 Leader，本地位点 | 无自动故障转移、无消费组代际，无法满足 v2 目标 |
| **客户端消费组** | 客户端自己分配分区、提交位点 | 无法在服务端做代际 fencing，脑裂时两个消费者会同时消费同一分区 |
| **Kafka 协议 / exactly-once** | 兼容 Kafka wire、事务性生产 | 与本仓契约模型/能力门禁冲突；ADR-0015 已列为非目标 |
| **专用日志分片（选中）** | 固定 Raft 分片池承载多个分区；状态机追加日志 | 复用 Region 表/Raft/快照/备份；分区数与 Region 数解耦；代价是热分片共享 Leader |

## 决定

### D1 定位与顺序

- MQ v2 是 v2 集群的**服务端**分区日志，不是 v1 的原地升级；v1 保持冻结。
- 代码可以在 `[mq_v2].enabled=true` 下提前落地和测试；**对外 GA（M7）不早于
  KV-T GA**（ADR-0015 D8）。在 GA 前 `coord.mq.v2` 状态为 PROPOSED，不写成
  COMMITTED。

### D2 复制单元：日志分片与消费组分片

- 用**固定的 Raft 分片池**承载 MQ 状态，分片是 Region 表里的正式条目：
  - 日志分片：保留区间 `/_mq/log/<shard_id>/`；
  - 消费组分片：保留区间 `/_mq/group/<shard_id>/`。
- 分片 Leader = 该 Region 的 Raft Leader；写（Publish/Ack/Join）只在该 Leader
  处理，非 Leader 返回 `NOT_LEADER` + leader hint。
- 分片数在启动时由 `[mq_v2].log_shards`（默认 8）与 `group_shards`（默认 4）
  决定；从 `initial_regions` 的种子表里切出保留区间，切不出来就启动失败。
  SplitChecker/MergeChecker 跳过 `/_mq/`（与 `/obj/` 同一类例外）。
- 不新增 RegionKind 字段：保留区间 + `Command::Mq*` 校验足够；新增 kind 需要
  改 Region 表/快照格式，收益不足。后续要做隔离增强时再加。
- **不做自动再平衡**：`CreateTopic` 按最少分区数把分区分配到日志分片；分片扩容
  只影响新 topic/新分区，已有分区不迁移。手工 `MovePartition` 留到 M7 之后。

### D3 存储模型：追加段日志

- 每个分区是追加段日志：段按 `segment_bytes`（默认 64 MiB）或年龄封口；消息记录
  含 offset、timestamp、key、headers、payload、producer 元数据。
- **offset 在 Raft apply 内分配**：每分区 `u64`、从 0 开始、严格递增、绝不复用。
  不把 `commit_ts`/MVCC revision 当 offset；MQ 不依赖 TSO 排序。
- `timestamp` 是服务端墙钟毫秒，只作观测/触发审计，**不是排序依据**；消费者只按
  offset 排序。
- 段日志是状态机状态：Snapshot 含段索引 + 段数据 + 幂等索引 + DLQ；恢复后 offset/
  段边界/位点不倒退。MQ 段不是 Raft log，不受 ADR-0004 的日志回收窗口约束。

### D4 写路径：Leader 批量追加

- `Publish`/`PublishBatch` 由服务端处理；客户端可发到任意节点，非分片 Leader 返回
  `NOT_LEADER`，客户端按 hint 重路由。
- Leader 侧按分片批量（默认最多 64 条或 2 ms，先到先发）把多个请求合成一条
  `Command::MqAppendBatch`；一次 Raft 提交、一次 fsync 摊薄多个请求。
- **响应即已提交**：Raft 多数派提交并 apply 后才返回 offset；不是“写本地缓存”。
- `PublishBatch` 以**单个分区的请求**为单位原子：批量内任一条超限/超配额则整批
  不追加；不同请求在同一 Raft 条目里各自成败，互不部分提交。
- 无幂等键的重复发布可能产生重复消息（at-least-once 生产）；调用方要重试就带
  `idempotency_key`。

### D5 投递语义：至少一次 + best-effort 推送

- **`Poll` + `Ack` 是唯一至少一次路径**：`Ack` 成功后位点前进；崩溃后从已提交位点
  续读；重复投递是正常形态，消费者必须按 `(topic, partition, offset)` 幂等。
- `Subscribe` 仍是**best-effort 推送**：背压时丢弃、不重投；它不是至少一次通道。
  需要可靠消费就用 `Poll` + `Ack`（或 SDK 的 consumer helper）。
- **不承诺 exactly-once**；不做跨分区事务；生产幂等只覆盖 `Publish` 的重复提交，
  不等于消费端 exactly-once。
- offset 是不透明 `u64`；`Poll` 的 `start_offset` 为 `optional`：未设置=由调用方
  决定（SDK 用已提交位点），显式设置且低于最早可用 offset 时返回
  `OFFSET_OUT_OF_RANGE`（附 earliest/latest），**不静默 clamp**。
- 支持长轮询 `wait_ms`（上限 30s）；超时返回空批，不是错误。

### D6 消费组：服务端协调 + 代际 fencing

- 新增消费组分片；每个组按组名哈希到固定 group shard，组 Leader = 分片 Leader。
- 组状态（成员、订阅、分配、代际、位点）持久化在 group shard 状态机；Leader
  换届后由新 Leader 从已 apply 状态继续，不丢组/位点。
- 协调在服务端完成：`JoinGroup` / `Heartbeat` / `LeaveGroup` /
  `GetCommittedOffsets` / `DescribeGroup` / `ListGroups`。v2.0 不做客户端自定义
  assignor、不做 `SyncGroup`；分配策略固定为按分区数的 range（后续可加 sticky）。
- 每次成员变化/会话过期，代际 `generation++`；同一 `(group, topic, partition)`
  在**一个代际内至多分配给一个成员**。`Ack` 必须带 `member_id` + `generation`，
  校验成员/分配/单调性；过期代际返回 `GROUP_EPOCH_STALE`，未分配返回
  `NOT_GROUP_MEMBER`。
- 会话过期由 Leader 周期提案 `MqGroupReap { now_ms }` 触发；apply 只使用命令里
  携带的时间，保证确定性。成员通过 `Heartbeat` 续期。
- **位点存在 group shard，不存在日志分片**：`Ack` 与代际校验在同一个 apply 内
  原子完成；`Poll` 只读日志分片，用调用方显式传入的 offset，不跨分片读组状态。
  SDK 的 consumer helper 在 Join/GetCommittedOffsets 后缓存位点。
- 组 shard 是单点（按组分片）；v2.0 用批量 `AckBatch` 摊薄。组数/吞吐超限时，
  后续按组名扩 group shard 或拆协调器，另立 ADR。

### D7 保留与容量

- **按时间保留**：topic 级 `retention_secs`，默认 7 天（1h–30d）；按整段回收，
  不逐条 TTL。至少保留一个段（最新段），避免空 topic 把最后一条也删掉。
- **按容量配额**：topic 级 `max_bytes`（默认 1 GiB，0=不限）；`max_message_bytes`
  默认 1 MiB（上限 8 MiB）；`max_partitions` 默认 256；每分片分区上限默认 1024。
- 记账户径 = 日志段物理字节 + DLQ 字节 + 幂等索引；不含组状态/位点（有界小表）。
  配额在 append apply 内检查，**超限拒绝整批**（`RESOURCE_EXHAUSTED` +
  `QUOTA_EXCEEDED`），不静默丢历史、不按最老段截断。
- 保留回收由分片 Leader 周期提案 `MqTruncate { partition, up_to_offset }`，apply
  删除整段并推进 `earliest_offset`；重放幂等。`Poll` 低于最早 offset 明确报
  `OFFSET_OUT_OF_RANGE`，让消费者知道历史已被保留策略删除。

### D8 幂等发布

- `(topic_id, partition, idempotency_key)` → 首次 offset；索引与消息在同一 apply
  内写，重启/Leader 换届后仍去重。空键不去重。
- 去重窗口 = topic 保留期（至少 1h）；窗口外允许同键重新使用，契约必须写明。
- 重复请求返回首次 offset，不重复追加、不重复计配额；同批内重复键按首次处理。
- 幂等索引计入容量；回收与消息段同水位。

### D9 死信（DLQ）

- 显式 `MoveToDlq(topic, partition, offset, reason, detail)`：把消息复制到该分区的
  DLQ 日志，并在主日志该 offset 写 tombstone；`Poll` 跳过 tombstone，`PollDlq`
  读 DLQ（带原 topic/partition/offset + reason/detail）。
- **不做通用消费者的自动投毒判定**（保留 v1 边界）；只有工作流触发器在
  `max_attempts` 后自动移 DLQ（D12），reason 固定可审计。
- DLQ 有独立 offset 与保留期（默认同 topic，可配）；主日志 tombstone 不缩短原段
  保留期，因此副本在窗口内双份计费——契约写明，容量按物理字节算。
- 移入是管理路径（`coord:mq:dlq`），不要求 `coord:mq:manage`。

### D10 Topic 元数据与生命周期

- topic 元数据（topic_id、name、partitions、config、epoch、partition→shard）存
  region 0 状态机；`CreateTopic`/`UpdateTopic`/`DeleteTopic` 是单条 Raft 命令，
  不经过客户端事务。
- `CreateTopic` 支持 `request_id` 幂等：同请求重放返回同 topic_id；同名不同配置
  返回 `ALREADY_EXISTS` + `TOPIC_EXISTS`。
- `DeleteTopic` 只标记 `deleted_epoch` 并返回 `delete_id`；之后读写立即
  `TOPIC_NOT_FOUND`。数据回收异步（逐分区 truncate + 组位点清理），
  `GetTopicDeletion(delete_id)` 返回进度/回收计数。同名可以立即重建（新
  topic_id，旧数据按旧 topic_id 隔离回收），不会复活旧消息。
- 数据面请求可带 `topic_epoch`（SDK 必须带；缺失视为 0=不校验，兼容简单脚本）；
  epoch 不匹配返回 `TOPIC_EPOCH_STALE`，防止删后重建时旧客户端写进新 topic。
- 不做自动分区再平衡/迁移；`MovePartition` 属于 M7 之后的后继工作。

### D11 契约、能力与部署面

- 新契约包 `coord.mq.v2`，service 名沿用 `MQ`；方法与字段在 M0 冻结。v1
  `coord.mq.v1` 不新增能力、不改 wire。
- 能力沿用 v1 名称：`coord:mq:manage`（topic 生命周期/Describe/List/Update）、
  `coord:mq:publish`、`coord:mq:consume`（Poll/Ack/组）、`coord:mq:subscribe`、
  `coord:mq:dlq`（MoveToDlq/PollDlq）。
- 服务端在 `CoordNode` 实现，`coord/src/main.rs` 注册；Agent 在
  `data_plane="v2"` 时经 `proxy_v2` 代理 `coord.mq.v2`，不再启动 v1 本地 MQ。
- `[mq_v2].enabled=false`（默认）时服务壳仍注册（reflection 可见）但一律
  `FAILED_PRECONDITION`；`enabled=true` 必须同时 `[kv_t].enabled=true`，否则启动
  失败并点名配置项。
- `services.mq=true` 在 v2 上的含义是“启用 MQ v2 代理”；MQ v1 在 v2 集群仍
  fail-closed。`services.workflow_durable=true` 在 v2 上要求 MQ v2 可用（D12）。

### D12 v2 Outbox、Workflow durable 与 MQ 触发

- **v2 outbox**：工作流状态与 outbox 记录用 `coord.txn.v2` 同一事务写；relay 以
  `event_id` 为 `idempotency_key` 投递 MQ v2；至少一次，重复由 MQ 幂等索引去重。
- **Workflow durable 上 v2**：工作流存储/审批聚合/outbox 切到 v2 KV/Txn；durable
  引擎与审批桥在 v2 上可用（关闭 B-KVT-6 的“v2 审批不可用”）。`coord.workflow.v1`
  公共语义不变；`WorkflowStartRequest` 增加可选 `idempotency_key`，同键重放返回
  首个 workflow_id。
- **MQ 触发器**：workflow 定义可声明 `trigger = { topic, filter, max_attempts }`；
  durable 引擎按定义加入消费组（组名按 definition_id 派生），`Poll` 消息 →
  以 `mq:<topic_id>:<partition>:<offset>` 为幂等键 `Start` 工作流 → **Start 持久化
  后**才 `Ack`。崩溃重投由 Start 幂等吸收；连续失败到 `max_attempts` 移 DLQ 并
  Ack。
- 触发器要求 topic 已存在（fail-closed，不静默 auto-create）；输入默认是消息信封
  （topic/partition/offset/key/headers/payload），不做模板语言。
- 多个 Agent 通过消费组分担触发分区；再平衡后从已提交位点续读，至少一次。

### D13 Gate、停止与不变量

- 交付按 M0 → M7 推进（见设计文档）；每个 gate 都有停止/回退选项，不得用沉没
  成本跳过。G7 GA 必须晚于 KV-T GA。
- 不变量：
  1. 每分区 offset 唯一、严格递增、绝不复用；保留只删除前缀；已提交位点单调。
  2. Publish 响应 ⇒ 消息已被多数派提交；Poll 只返回已提交消息；批量原子。
  3. 一个代际内一个分区至多一个消费者；过期代际不能 Ack。
  4. 消息要么在日志、要么被 tombstone 移入 DLQ、要么被保留策略删除；后者必须
     由 `OFFSET_OUT_OF_RANGE` 显式暴露，不静默跳过。
  5. 配额拒绝是 apply 内确定性的整批拒绝；不产生部分消息。
  6. DeleteTopic 后旧 topic_id 的读写一律 `TOPIC_NOT_FOUND`；回收幂等；topic_id
     不复用。
  7. 分片/组 Leader 换届后已提交消息、offset、位点不倒退。
  8. v1 MQ 不在 v2 集群服务；v2 MQ 不在 v1 集群服务；无 v1→v2 迁移。
  9. 触发器：Start 未持久化不 Ack；重复 Start 由幂等键吸收；毒消息进 DLQ 后可审计。

## 后果

### 收益

- MQ 从 Agent 本地静态 ISR 升级为 Region/Raft 承载的持久分区日志：Leader 自动
  故障转移、服务端消费组、位点可迁移、容量/保留可控。
- 复用 KV-T 的 Region 表、快照/备份、Agent v2 代理与契约工具链，不另造一套复制层。
- 工作流 durable/审批/MQ 触发可以在 v2 上闭环，不再被 B-KVT-6 挡住。

### 代价与风险

- **热分片**：同一日志分片上的分区共享 Leader/fsync；`[mq_v2].log_shards` 是扩容
  旋钮，但 v2.0 不做自动再平衡。
- **组 shard 单点**：按组分片，组多/ack 多时是瓶颈；用 `AckBatch` 摊薄，后续按
  组名扩分片。
- **DLQ 双份存储**：tombstone 不缩短主段保留期，窗口内主消息 + DLQ 各一份。
- **段日志快照**：快照大小受保留期/配额约束；需要 snapshot 限速与恢复测试。
- **工作流迁移面大**：v2 outbox/durable/审批桥同时切换，必须与 MQ v2 分阶段验收。
- **不做 exactly-once/自动再平衡/分区 split/merge**：这些是明确的 v2.0 非目标，
  需要后续 ADR/版本。
- **双份契约维护**：v1 MQ 冻结但仍要修 security/bug；v2 是新增面。

### 与既有 ADR 的关系

- 不推翻 ADR-0001/0002/0004/0010/0013/0014/0015；MQ v2 在 KV-T 之上新增能力。
- ADR-0015 D8 的顺序依赖不变；本文是其 G7 的落地 ADR。

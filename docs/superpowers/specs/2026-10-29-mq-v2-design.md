# MQ v2 设计与 G7 任务拆分

> Owner: maintainers ｜ Last verified: 2026-10-29 ｜ 状态：设计已签（ADR-0016），M0 待启动
>
> 语义单一归属：`docs/adr/0016-mq-v2.md`（决定）与 `docs/adr/0015-kv-t.md`（v2 基座）。
> 本文只描述架构、工作项、依赖与验收；不重复 ADR 的承诺文本。任务状态以 issue 为准，
> gate 证据以 `docs/production/ops/mq-v2-gate.md` 为准。

## 1. 意图

KV-T 已把 v2 集群做成「Region 表 + Raft 组 + 快照/备份 + v2 数据面」的基座，但 MQ 仍是
Agent 本地的 v1：静态 ISR Leader、Leader 本地位点、没有真正的消费组。v2 集群上 MQ v1
fail-closed，依赖 MQ 的 workflow durable/审批/触发也因此不可用（B-KVT-6）。

MQ v2 要在 v2 基座上补一个**服务端分区日志**，让 coord 的内部队列/事件/工作流触发不再
依赖单 Agent：

1. 分区内严格有序、至少一次消费、消费组协调、位点可恢复；
2. 保留/配额/死信/删除可运维，不静默丢数据；
3. 工作流 durable 与审批在 v2 上闭环，MQ 消息可以直接触发 workflow；
4. 只服务 greenfield v2，不迁移 v1，不承诺 Kafka 兼容/exactly-once。

## 2. 目标、非目标、反目标

### 目标

- `coord.mq.v2` 契约与实现：Create/Describe/List/Update/DeleteTopic、Publish/
  PublishBatch、Poll/Ack/AckBatch、Join/Heartbeat/LeaveGroup、GetCommittedOffsets/
  DescribeGroup/ListGroups、Subscribe、MoveToDlq/PollDlq、GetTopicLeader。
- 分区日志随 Region/Raft 复制；分片 Leader 自动故障转移；已提交消息/位点不丢不倒退。
- 服务端消费组：代际 fencing、会话过期、分区唯一分配、lag 可观测。
- 保留/配额/幂等/DLQ/删除回收的语义在 apply 内确定，不靠周期性“尽力而为”。
- v2 工作流：v2 outbox、durable 引擎、审批桥、MQ trigger 全链路可用。
- Rust/Java SDK、Agent v2 代理、监控/runbook/备份/混沌/Jepsen 证据齐全。

### 非目标（v2.0 不做）

- Kafka wire 兼容、连接器/流处理、跨集群复制。
- exactly-once / 事务性消费 / 跨分区事务。
- 全局（跨分区）顺序；只承诺分区内顺序。
- MQ v1 数据迁移或 v1/v2 双写；v2 集群只从空 topic 开始。
- 自动分区再平衡/迁移、在线 split/merge 单个分区。
- 消息体压缩、分层存储、按 key 的 compacted topic。
- 自动投毒判定（通用消费者）；只有工作流触发器有 `max_attempts` 策略。

### 反目标（即使“能跑”也算失败）

- 为了复用 KV 而把消息塞进 MVCC，保留期靠逐 key tombstone/DeleteRange，容量随历史
  消息线性膨胀。
- 把 offset 建成非确定性（Leader 本地时钟/随机/可回退），或允许保留后静默 clamp。
- 消费组没有代际 fencing，两个消费者同时消费同一分区。
- `Ack` 先回成功再持久化，或 Start workflow 先回成功再落库。
- 关闭 `[mq_v2]` 时改变 v1 MQ/Agent 的默认行为。

## 3. 现状与约束

| 约束 | 对本设计的影响 |
|:--|:--|
| ADR-0001 默认关闭 | `[mq_v2].enabled=false` 时零副作用；服务壳注册但 `FAILED_PRECONDITION` |
| ADR-0015 D7/D13 v1 冻结、v2-only | v1 MQ 不新增能力；v2 不服务 MQ v1；不写迁移工具 |
| ADR-0015 D8 G7 顺序 | 代码可提前落在 flag 后；M7 GA 不早于 KV-T GA |
| ADR-0004 快照锚定 Raft GC | MQ 段是状态机状态，随 Region 快照/整节点备份；不是 Raft log |
| 契约纪律 | 字段语义写 `coord.mq.v2` proto 头注；错误码只按码分支 |
| 现有 v1 容量边界 B-PL-4 | v2 要把“逐写严格上界”升级为段级记账，不退回事后淘汰 |
| Agent v2 代理模式 | MQ v2 服务端实现；Agent 只代理，不启本地 redb |

v1 的事实基线（代码/契约）见 ADR-0016 背景表，不在本文重复。

## 4. 方案与选中理由

| 方案 | 取舍 | 结论 |
|:--|:--|:--|
| KV 承载日志（commit_ts/计数器 offset） | 复用最大，但 MVCC 写放大、保留只能逐 key 删、配额/幂等不能 apply 内严格 | 不选；小 topic 后备 |
| 一分区一 Region | 隔离最好，但分区数放大 Region/副本数，CreateTopic 进热路径 | v2.0 不选；隔离增强再做 |
| 固定日志分片池（选中） | 分区与 Region 解耦，复用 Region 表/Raft/快照；热分片共享 Leader | **选中** |
| 静态 ISR（v1） | 无自动故障转移/组代际 | 不选 |
| 客户端消费组 | 无服务端 fencing，脑裂 | 不选 |
| Kafka 协议/exactly-once | 非目标，契约/能力模型冲突 | 不选 |

选中方案的完整决定见 ADR-0016 D2–D13。

## 5. 架构

### 5.1 组件

```text
client / SDK
   │  coord.mq.v2（Publish/Poll/Ack/Join/...）
   ▼
coord-agent proxy_v2::MqV2Proxy ──► coord server（任意节点）
                                      │
                    ┌─────────────────┼──────────────────┐
                    ▼                 ▼                  ▼
              region 0 状态机     日志分片 Raft 组     消费组分片 Raft 组
              topic 元数据        offset/段/幂等/DLQ   成员/代际/分配/位点
                    │                 │                  │
                    └────────── Region 表 / 快照 / 整节点备份 ──────────┘
```

- **region 0**：topic 元数据与 topic_id/epoch；Create/Update/Delete 单条 Raft 命令。
- **日志分片**（`[mq_v2].log_shards`，默认 8）：每个分片一个 Raft 组，承载若干分区；
  保留区间 `/_mq/log/<shard_id>/`。Leader 处理 Publish/Poll/MoveToDlq/Truncate。
- **消费组分片**（`[mq_v2].group_shards`，默认 4）：按组名哈希；承载成员、代际、分配、
  位点；保留区间 `/_mq/group/<shard_id>/`。Leader 处理 Join/Heartbeat/Leave/Ack。
- **Agent**：`data_plane="v2"` + `services.mq=true` 时启 `MqV2Proxy`，把
  `coord.mq.v2` 转发到 server；不启动 v1 `MessageQueueService`。
- **PD/Region 表**：分片是正式 Region；SplitChecker/MergeChecker 跳过 `/_mq/`；
  分片数在启动时切出保留区间，切不出就 fail-closed。

### 5.2 数据布局

| 数据 | 位置 | 说明 |
|:--|:--|:--|
| topic 元数据 | region 0 | `topic_id`、name、partitions、config、epoch、partition→shard |
| 消息段 | 日志分片 | 每分区按 offset 追加；段大小/年龄封口；offset 在 apply 分配 |
| 幂等索引 | 日志分片 | `(topic_id, partition, key) → offset`，与消息同 apply 写 |
| DLQ | 日志分片 | 独立 offset/保留；主日志 tombstone 标记已移入 |
| 组/成员/分配/位点 | 消费组分片 | 每代际一份分配；位点按 `(group, topic, partition)` 单调 |

### 5.3 写路径

1. 客户端 → 任意节点；服务端查 topic 元数据（缓存 + epoch）→ 分区所属日志分片。
2. 非 Leader → `NOT_LEADER` + hint；客户端刷新后重试。
3. Leader 把同分片的多个请求合成一条 `Command::MqAppendBatch`（最多 64 条 / 2 ms）。
4. Raft 多数派提交 + apply：分配 offset、检查配额/大小/幂等、写段、更新索引。
5. apply 结果按请求返回；`PublishBatch` 单分区原子：任一条失败整批不追加。

### 5.4 读/消费路径

- `Poll` 只发日志分片 Leader；读已 apply 状态，不发 Raft 提案。长轮询由分片 append
  通知唤醒，超时返回空批。
- `start_offset` 显式；低于最早 offset → `OFFSET_OUT_OF_RANGE`（带 earliest/latest）；
  高于 latest → 空批/等待。
- `Ack`/`AckBatch` 发消费组分片 Leader；apply 校验成员/代际/分配/单调，再写位点。
- SDK consumer helper：Join → GetCommittedOffsets → Poll → 处理 → Ack → Heartbeat；
  收到 `REBALANCE_IN_PROGRESS`/`GROUP_EPOCH_STALE` 时重新 Join。

### 5.5 组协调

- `JoinGroup(group, member_id?, topics, session_timeout_ms)` → member_id、generation、
  分配（topic/partition 列表 + 已提交位点）。
- 成员变化/过期 → generation++，重新分配；`Heartbeat` 续期，过期由 Leader 的
  `MqGroupReap { now_ms }` 提案清理。
- 一个代际内一个分区至多一个成员；Ack 必须带 member_id + generation。
- v2.0 不做客户端 assignor/SyncGroup；分配策略固定 range。

### 5.6 保留、配额、删除

- 保留按整段回收（默认 7d，1h–30d）；至少保留最新段；`earliest_offset` 随段前进。
- 配额 = 段字节 + DLQ + 幂等索引；append apply 内严格检查，超限整批拒绝。
- `DeleteTopic` 标记 epoch、立即 `TOPIC_NOT_FOUND`、异步逐分区 truncate；同名重建
  得到新 topic_id，旧数据按旧 id 回收，不复活。

### 5.7 工作流触发

- workflow 定义声明 `trigger = { topic, filter, max_attempts }`；topic 必须已存在。
- durable 引擎按 definition_id 加入消费组，Poll 消息 → 以
  `mq:<topic_id>:<partition>:<offset>` 为幂等键 Start → Start 持久化后 Ack。
- 连续失败到 `max_attempts` → MoveToDlq + Ack + 指标；输入是消息信封，不做模板语言。
- v2 outbox 与工作流状态用同一 v2 Txn 写；relay 以 event_id 为幂等键投递 MQ v2。

### 5.8 API、错误码、能力

- 包 `coord.mq.v2`，service `MQ`；方法与字段在 M0 冻结。
- 结构化错误码（初稿，M0 定稿）：`TOPIC_NOT_FOUND`、`TOPIC_EXISTS`、
  `TOPIC_EPOCH_STALE`、`PARTITION_NOT_FOUND`、`OFFSET_OUT_OF_RANGE`、
  `GROUP_NOT_FOUND`、`NOT_GROUP_MEMBER`、`GROUP_EPOCH_STALE`、
  `REBALANCE_IN_PROGRESS`、`MESSAGE_TOO_LARGE`、`QUOTA_EXCEEDED`。
- 能力沿用 v1：`coord:mq:manage` / `publish` / `consume` / `subscribe` / `dlq`。
- 非 Leader 写 → `NOT_LEADER` + `coord-leader-hint`；客户端只按码/hint 分支。

### 5.9 配置与部署

```toml
[mq_v2]
enabled = false             # 默认关闭；requires [kv_t].enabled = true
log_shards = 8              # 启动时切出 /_mq/log/<id>/ 保留区间
group_shards = 4            # 启动时切出 /_mq/group/<id>/
max_partitions_per_shard = 1024
default_retention_secs = 604800
max_topic_bytes = 1073741824
max_message_bytes = 1048576
segment_bytes = 67108864
poll_max_bytes = 4194304
poll_max_messages = 1000
long_poll_max_ms = 30000
group_session_timeout_ms = 30000
```

- `enabled=false`：服务壳注册、reflection 可见、一律 `FAILED_PRECONDITION`；不切区间、
  不起分片、不启后台任务。
- `enabled=true` 但 `[kv_t].enabled=false` / 分片区间切不出 / 与 v1 MQ 装配冲突 →
  启动失败并点名配置项。
- `coord dev` 的 v2 预设可以在 M6 打开 MQ v2；生产默认关闭到 M7 GA。

## 8. 风险与开放问题

1. **热分片**：同一分片多分区共享 Leader/fsync；默认 8 分片是否够？M6 基准给数字，
   不够则调 `log_shards` 或做 MovePartition（post-GA）。
2. **组 shard 吞吐**：所有 Ack 落组 shard；`AckBatch` + 4 分片是否够？M6 压测；
   不够则按组名扩分片（新 ADR）。
3. **快照大小**：段数据随 Retention 增长；需要 snapshot 限速/恢复时间预算（M1-6/M6-3）。
4. **DLQ 双份存储**：主段保留期内双份计费；配额默认 1 GiB 是否合理？M6 容量报告。
5. **触发语义**：workflow Start 的幂等键是新字段，需契约变更（M5-3）；`max_attempts`
   默认值与退避策略需 M5 定稿。
6. **v2 工作流迁移面**：outbox/durable/审批同时切；M5-2 是高风险任务，需独立
   review + 回退开关。
7. **删除/重建 epoch**：`topic_epoch` 在数据面是否强制？M0 契约定稿；SDK 必须带。
8. **保留删除与已提交位点**：位点低于 earliest 的组在下次 Poll 会 `OFFSET_OUT_OF_RANGE`；
   需要 SDK 的 reset policy（earliest/latest/fail），M3-4 定。

## 9. Review Focus

- **关闭时零副作用**：`[mq_v2].enabled=false` 不得切区间、起分片/后台任务、改 v1 服务
  表/磁盘布局；启动日志只多一行。
- **提交后才可见**：Publish 响应/ Poll 结果必须来自已提交 apply；不能把 Leader 本地
  未提交缓冲读出去。
- **代际 fencing**：Ack 的 member/generation/assignment 校验必须在 apply 内；不能先在
  handler 内存判断再写。
- **offset 不复用**：保留/删除/重建/恢复后 offset 不倒退、不复用；topic_id 隔离。
- **配额原子性**：超限/超大整批不写；不能先写后删或部分写。
- **触发器不丢不重**：Start 持久化后才 Ack；重复 Start 由幂等键吸收；毒消息可审计。
- **v1 字节级不变**：`[mq_v2]` 关闭时 v1 MQ 的 wire/磁盘/默认行为不变。

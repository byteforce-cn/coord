# Spike 1 · 缺口清单（无法表达项 / 未决语义 / 需 EIS-ICPS 确认）

> Owner: Spike 执行（AI 协作者）｜ Last verified: 2026-10-13
> 口径：模型层已验证的可表达性 + **必须由业务确认**的语义空白。
> 对齐手册 §4 Spike 1「记录无法表达的语义」要求。

## 1. 结论摘要

- 手册 §3.2 的全部 P0（会签/加签/驳回至节点/转办/一票否决/或签/撤回）与
  已实现 P1（减签/委派/票签/阅签/终止）在 **模型层均可表达**，16/16 用例通过。
- **没有「无法表达」的 P0 语义**；但存在 13 项未决语义/未覆盖能力，其中
  Q1–Q6 必须由 EIS/ICPS 在正式清单中回答，否则实现时会替业务做决定。

## 2. 无法表达项

无 P0 级无法表达项。

| 语义 | 状态 | 说明 |
|:--|:--|:--|
| 会签 / 加签 / 减签 | ✅ 可表达 | `JoinPolicy::All` + 动态增删席位 |
| 驳回至节点 | ✅ 可表达 | 白名单 + attempt + jump_count；重开需调用方给审批人名单（Q7） |
| 转办 / 委派 | ✅ 可表达 | assignee 变更 / delegation 记录 |
| 一票否决 / 或签 / 票签 | ✅ 可表达 | `RejectPolicy` + `JoinPolicy` |
| 阅签 | ✅ 可表达 | `TaskKind::ReadAck`，不计票 |
| 撤回 / 终止 | ✅ 可表达 | 发起人校验 / 管理路径 |
| 流程级并行分支（并行网关） | ❌ 未覆盖 | 同一实例同时最多一个 open 分支（Q8） |
| 嵌套子流程的结果记账 | ❌ 未覆盖 | `parent_branch_id` 已留，父分支收口未实现（Q9） |

## 3. 未决语义（需业务确认）

| # | 问题 | 本原型临时口径 | 影响 |
|:--|:--|:--|:--|
| Q1 | 转办后原审批人是否保留审批权？ | **失去**审批权，仅保留 `transferred_from` 审计链 | 权限判定与审计口径；若保留需改为双人可批 |
| Q2 | 减签是否允许移除**已投票**的席位（撤票）？ | **不允许**；撤票只能走驳回/重开 | 会签中途撤票的业务场景无法支持 |
| Q3 | 票签/会签的分母如何计算：弃权、阅签、取消、过期席位是否计入？ | 阅签不计、取消不计、过期不计；**无弃权票型** | 票签阈值语义；需与 EIS 逐项对齐（与 R1 同源） |
| Q4 | 超时（deadline）到期后的处置：自动通过/自动驳回/升级上级/仅提醒？ | 仅置 `expired` 且**不计票**；无自动判定 | 超时审批的最终结果；影响 `total_count` 口径 |
| Q5 | 一票否决的作用域：只终止当前分支，还是整实例？ | **整实例** rejected | 若业务要求「否决当前节点但流程可继续」需扩展分支级否决 |
| Q6 | 授权模型：谁可加签/减签/驳回/终止/代批？职责分离（发起人不可自批？） | 模型仅记录 `by` + 审计，**无权限判定** | 审批系统合规底线；必须单独设计（现有 RBAC 只到 RPC 能力粒度） |
| Q7 | 驳回后重开节点，审批人是自动沿用原名单还是重新指定？ | 调用方在 `open_approval` 重新指定 | 影响「驳回后原审批人是否需重新审批」的手册缺省问题 |
| Q8 | 是否需要流程级并行分支（多节点同时 open）与 join 条件？ | 未支持（会签已在轮次内解决） | 若需要，需扩展 open 分支集合 + join 记账 |
| Q9 | 子流程/嵌套分支的完成如何回写父分支？ | 未实现 | 与 coord 现有 `run`（子流程）语义对接时必需 |
| Q10 | 实例与定义版本绑定：同版本内容覆盖/定义漂移如何防？ | 仅固定 ns/name/version，**无 definition_hash** | 与评估报告 G5 一致；属定义层治理（Spike 1 之外） |
| Q11 | 并发写路径：实例租约/fencing token 如何落 KV？ | 模型层 `revision` CAS 已就位 | 属 Spike 2 验证范围 |
| Q12 | 事件投递：Outbox/顺序/幂等键契约？ | 仅产出 `Effect::Event` 数据 | 属 Spike 3 验证范围 |
| Q13 | 变量写入 API 与可见性/权限规则？ | 仅读取（`resolve_var`），写入未提供 | 审批表单回填、驳回时携带修改数据需要 |
| Q14 | 「阅签不影响流程」：只有阅签的节点是否应立即通过？ | **立即通过**（total=0 视为通过） | 若业务要求等待阅签完成才继续，需改为阅签门 |

## 4. 对 Spike 6 形态决策的输入

- 扩展现有 `coord-core/workflow` 的**状态模型层**可行：本原型证明核心 P0 语义
  可以用新增实体层（Branch/Task/Round/Scope）+ 既有实例状态机表达；
- 真正的迁移成本不在状态机，而在：
  1. 授权与职责分离（Q6，需新契约）；
  2. 与既有 `coord.workflow.v1` RPC/事件/存储页的兼容（G2/G3/G5）；
  3. 并发分支/子流程的记账（Q8/Q9，若需要）。
